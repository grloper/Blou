## Spike results (offline)

### N4 follow-up: strict pinning proven offline

`blou-rdp::tls` uses an always-on Rustls verifier because the upstream callback only executes on validation failure. Source at the same pinned commit confirms this control flow; the self-signed Strict callback control passes in tests. Nine fixture tests prove matching pins, missing/mismatching pins (all 256 single-bit SHA-256 mutations), malformed matching bytes, a leaf that actually validates against an isolated trusted CA, and in-memory TLS 1.2/1.3 handshake match/mismatch controls. CA trust cannot bypass the custom verifier's pin check. Evidence: `docs/verification/rust-pinning.md`.

The configured pin is the trust authority. Rustls parses X.509 and rustls/ring verifies handshake signatures; no custom cryptography, OS trust-store changes, TOFU or user override. The config disables resumption and TLS key logging. Transport integration still must use this exact config; real RDP/Android enforcement remains UNVERIFIED. Rustls 0.23.41 from the upstream lockfile failed the advisory check for RUSTSEC-2026-0285; Blou pins the patched 0.23.45 instead. IronRDP itself remains unmodified.

Spike crate: `spike/ironrdp-multimon` on branch `spike/ironrdp-multimon`, pinned to the git rev above (a crates.io pin is impossible for finding #4).

`cargo test`: **6 passed, 0 failed**; `cargo clippy --all-targets -- -D warnings` clean; `cargo fmt` applied.

- `monitor_data_pdu_bytes_are_exact`: 3x(1920x1080) encodes to 68 bytes `flags=0,count=3` then monitors `(0,0,1919,1079,PRIMARY)`, `(1920,0,3839,1079,0)`, `(3840,0,5759,1079,0)`, equal to hand-computed bytes.
- `connector_emits_three_monitors_in_gcc_client_blocks`: drives the real `ClientConnector` (X.224 request, synthetic HYBRID confirm, CredSSP gate, Basic Settings) and decodes the emitted MCS Connect-Initial: 3 monitors, core desktop 5760x1080, `SUPPORT_MONITOR_LAYOUT_PDU` set.
- `monitor_block_omitted_if_server_lacks_extended_client_data`: no monitor block without `EXTENDED_CLIENT_DATA_SUPPORTED`.
- `seventeen_monitors_rejected_by_encoder`, DISPLAYCONTROL layout PDU byte check (136 bytes for 3 monitors incl. header), two-primaries rejected, odd width auto-adjusted.
- Mutation check: changing inclusive `right = left+w-1` to `left+w` made 2 tests fail, so the byte assertions are live.

## Phase 0 gate: still UNVERIFIED

### N6 follow-up: configuration works offline; adoption blocked

The workspace config builder re-runs all six spike cases at the same unmodified revision, plus pin/NLA/range controls. GCC bytes still match the three-monitor fixture; this does not prove Windows acceptance or authentication. Adding `ironrdp-connector` brings an audited graph containing `rsa 0.10.0-rc.18` (RUSTSEC-2023-0071, no patched upgrade) and unmaintained `atomic-polyfill 1.0.3` through SSPI/winscard. Both security scans fail; no exceptions or engine patches were added. Native Android preflight also fails in ring's C compiler setup. Details: `docs/verification/rdp-config.md`. N6 remains unchecked, FreeRDP stays as fallback, and live tests remain UNVERIFIED. Exact hardware checklists and current non-runnable steps: `docs/HARDWARE_GATES.md`.

The spike proves only that IronRDP *emits* the fabricated layout. Whether Windows 11 creates 3 displays is unproven. Human checklist (needs a Windows 11 Pro host with RDP+NLA on a Tailscale address and an account allowed to log on):

1. On the Windows host: Settings > System > Remote Desktop on; note the machine's tailnet address (placeholder `100.64.0.10`); confirm no existing console/RDP session for the same user (sign out other sessions).
2. From a Linux/macOS/Windows client with a single display, follow `docs/HARDWARE_GATES.md` once the native pinning block is resolved, **and** record the result. The probe currently supports preparation only; its live launch is blocked because the CLI fingerprint allowlist does not enforce a pin on a CA/name-valid mismatching leaf. (FreeRDP is the baseline; if it fails, IronRDP will not do better.)
3. Inside the RDP session run PowerShell: `Get-CimInstance -Namespace root\wmi -ClassName WmiMonitorBasicDisplayParams | Measure-Object` and `Add-Type -AssemblyName System.Windows.Forms; [System.Windows.Forms.Screen]::AllScreens | Format-Table DeviceName,Bounds,Primary`. PASS = 3 screens with bounds `0,0,1920,1080`, `1920,0,...`, `3840,0,...`, primary at origin. Also open Settings > System > Display and screenshot (redact hostnames).
4. Repeat with the IronRDP build once the `blou-rdp` connect task lands (same host, same checks). Record host Windows build (`winver`), client commit, pass/fail, and any server-side event log entries.
5. Negative controls: try 1 monitor and 4 monitors; try after reconnect.
6. Report to the owner; do not proceed to Android UI work on IronRDP until step 4 passes.
